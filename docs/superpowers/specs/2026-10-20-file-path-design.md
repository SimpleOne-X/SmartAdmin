# 文件路径设计（业务文件按配置落到文件服务器）

## 一、目标与边界

很多业务附件不放在应用服务器上，而是放在 NAS 这类文件服务器上，不同业务放不同文件夹。
现在每个业务自己拼路径、自己起文件名、自己写上传下载接口，校验和鉴权各写各的。

本设计在内核里新增「文件路径」：
管理员先登记文件服务器（根路径和访问账号），
再按行配置每类业务文件存到哪台服务器的哪个文件夹、怎么命名、能传什么、谁能上传、谁能下载；
业务用**编码**调统一的上传接口，拿回**相对路径**存进自己的业务表，下载时带着编码和相对路径调统一的下载接口。

做：

- 两张新表：`sys_file_server`（文件服务器）、`sys_file_path`（文件路径）。
- 新页面「文件管理 → 文件路径」，分「文件路径」「文件服务器」两个页签。
- Windows 上由内核用文件服务器的账号建立连接，密码加密存库。
- 上传接口和下载接口，分属两个控制器、两个服务，路由也分开。
- 三种命名规则（年/月/原名_短ID、业务指定路径、日期/GUID），另有「只读」开关。
- 每行单独配置上传角色和下载角色。
- 签名直链：给 `<img>` 预览和不带令牌的客户端用，由后端按需签发、带有效期。
- 配置页的测试连接和在线状态。

不做：

- **不碰现有上传。** `sys_file` 表、`IFileService`、`IFileStorage`、`IChunkStorage`、`IFileUrlSigner`、
  `/api/v1/sys/file/*` 接口、`FileUpload` 组件、配置中心「上传策略」分组，全部不改，新功能也不调用它们。
  新功能是一套独立的上传下载，两套互不影响。
- 不记上传记录。没有 `sys_file` 这样的行，文件路径只存在业务表里。
- 不扫描文件夹、不统计文件数、不做文件浏览器。文件特别多的文件夹也不影响配置页。
- 不提供按任意绝对路径下载的接口；下载的相对路径只能落在某一行的文件夹里。
- 不提供 HTTP 删除接口。删除只有后端服务方法，由业务在删单据、换附件时调用。
- 不回收孤儿文件（传上去了但业务表单没保存的文件）。按年月分文件夹，方便人工清理。
- 不做秒传，不做自动搬文件。
- Linux / Docker 上内核不自己连接文件服务器。
  在 Linux 上连 SMB 要么挂载（需要宿主机权限），要么引入第三方 SMB 客户端库，后者违反核心包只依赖 SqlSugarCore + Microsoft.\* 的约束。
  Linux 上由宿主机挂载，账号写在挂载凭据里（见 8.2）。

## 二、术语

| 术语 | 含义 |
|---|---|
| 文件服务器 | `sys_file_server` 的一行：根路径 + 访问账号。一台 NAS 的一个共享登记一行 |
| 文件路径 | `sys_file_path` 的一行配置，用编码标识 |
| 编码 | 业务代码引用一行文件路径的唯一依据，如 `Order.Attachment`、`PrintTemplate` |
| 文件夹 | 一行文件路径实际读写的目录 = 文件服务器的根路径 + 这一行的子文件夹，如 `\\nas01\files` + `Order/Attachment` |
| 相对路径 | 上传接口返回、业务表保存的值，相对这一行的文件夹，统一用正斜杠，如 `2026/10/报价单_3f9c2e1a.pdf` |
| 根目录白名单 | 运维在 appsettings 里放行的根目录，可选。配了它，所有文件服务器的根路径都必须落在其中某一个下面 |

## 三、数据模型

### 3.1 `sys_file_server`

| 字段 | 类型 | 说明 |
|---|---|---|
| `Name` | string(100)，唯一，输入最多 64 字符 | 名称，如 `nas01-files`。列比输入长，是给软删时追加的 `_del_{id}` 留位置 |
| `RootPath` | string(260) | 根路径，绝对路径。Windows 上写共享 `\\nas01\files`，Linux 上写挂载点 `/mnt/nas01-files`，也可以是本机目录。配了根目录白名单时必须落在其中，没配时不能碰程序目录和分片暂存目录 |
| `UserName` | string(128)，可空 | 访问账号，`域\账号` 或 `账号`。空 = 用后端自己的运行身份访问 |
| `PasswordProtected` | string(2048)，可空 | 密码经 `ISecretProtector` 加密后的信封 |
| `Enabled` | bool | 停用后，挂在它下面的文件路径全部不能上传、下载 |
| `Remark` | string | 备注 |

- 密码的处理和 AI 厂商的 API Key 一样：
  接口从不返回密码，只返回「已设置」；编辑时留空表示不改；
  数据保护密钥是进程内临时密钥时拒绝保存密码，因为重启后就解不开了。
  清空账号时一并清空密码。
- 填了账号时，根路径必须是 `\\主机\共享` 开头的共享路径：账号只用来在 Windows 上建立 SMB 连接。
- **同一台主机只能用同一个账号。**
  Windows 的 SMB 客户端在同一个登录会话里，对同一台服务器只接受一套凭据，第二套会返回 1219（凭据冲突）。
  所以修改一行的账号或密码时，根路径主机名相同的其他行一起改成同一套（清空账号也一起清空）。
  新增一行、或把一行换到另一台主机时，账号和那台主机已有的行不一致就拒绝（不区分大小写，空也算一种）。
  修改时换了主机或账号而密码留空，拒绝保存，要求重新填写密码。
  主机名按写法比较，`\\nas01` 和 `\\192.168.1.10` 算两台。
- 被文件路径引用的文件服务器不能删除。

### 3.2 `sys_file_path`

| 字段 | 类型 | 说明 |
|---|---|---|
| `Code` | string(100)，唯一，输入最多 64 字符 | 编码。只允许字母、数字、`.`、`_`、`-`；保存后不能修改 |
| `Name` | string(100)，输入最多 64 字符 | 名称 |
| `ServerId` | long | 文件服务器 |
| `Folder` | string(260) | 子文件夹，相对文件服务器的根路径，正斜杠分隔；空 = 根路径本身 |
| `NamingRule` | 枚举 | `YearMonthOriginal` 年/月/原名_短ID、`BusinessPath` 业务指定路径、`DateGuid` 日期/GUID |
| `OnConflict` | 枚举 | `Reject` 拒绝、`Overwrite` 覆盖；只对 `BusinessPath` 有意义 |
| `ReadOnly` | bool | 只读：不开放上传，只提供下载，测试连接只测读 |
| `AllowedExtensions` | string，可空 | 允许的后缀，小写带点、逗号分隔。可写的行**必填**，只读的行不填。不继承「上传策略」，两套上传互不影响 |
| `MaxSizeMb` | int，可空 | 单个文件上限（MB）。可写的行必填且大于 0，只读的行不填 |
| `UploadRoleIds` | string | 可上传的角色 Id，逗号分隔；空 = 所有登录用户 |
| `DownloadRoleIds` | string | 可下载的角色 Id，逗号分隔；空 = 所有登录用户 |
| `Enabled` | bool | 停用后上传、下载、签名直链都拒绝 |
| `Remark` | string | 备注 |

角色存成一列而不建关联表：鉴权时只看当前这一行，用不着反查「某个角色能访问哪些行」。

两张表在每次上传、下载时都要读，走内核缓存，增删改时失效。

改文件服务器或子文件夹不会搬走已有文件，业务表里的相对路径会指向新文件夹。配置页编辑时提示这一点。

### 3.3 配置项 `SmartAdmin:FilePath`

新增 `AdminFilePathOptions`，不往现有的 `AdminUploadOptions` 里加字段：

| 配置 | 默认 | 说明 |
|---|---|---|
| `AllowedRoots` | 空数组 | 根目录白名单。空 = 根路径直接在界面填，只避开程序目录和分片暂存目录（见 4.1） |
| `StagingPath` | `./data/file-path-staging` | 分片暂存目录，相对路径按 ContentRoot 解析 |
| `StagingTtlHours` | 24 | 分片会话多久没有新分片就视为放弃，暂存清掉 |
| `LinkTtlMinutes` | 60 | 签名直链默认有效期，签发时可以另传 |

根目录白名单放在 appsettings 而不是界面里，因为它是安全边界：
界面上的管理员如果能随便填根路径，就能把文件写进服务器的程序目录、静态站点目录，
或者用 `\\127.0.0.1\c$\…` 这类共享路径绕回本机。
文件服务器在界面上维护，白名单限定它能指到哪里，
和 AI 厂商的调用地址在界面上填、出站围栏在 appsettings 里配是同一个思路。
加一个新共享要改 appsettings 并重启，这件事很少发生，由能登录服务器的运维来做。

白名单是可选的。不配时根路径直接在界面填，只避开程序目录（`AppContext.BaseDirectory`）和分片暂存目录，
拦不住 `\\127.0.0.1\c$\…` 这类绕回本机的共享路径，边界退到能改文件服务器的账号本身（部署方只把这个页面给超管）。

## 四、路径与命名规则

### 4.1 校验

- **文件服务器的根路径**：必须是绝对路径；配了白名单时，规范化（`Path.GetFullPath`）后等于某个白名单根目录，或在它下面
  （按「根目录 + 分隔符」前缀判断，免得 `\\nas01\files2` 误匹配 `\\nas01\files`）。
  没配白名单时，根路径等于、落在、包含程序目录或分片暂存目录都拒绝（`44158`），配了白名单时不在名单内拒绝（`44152`）。
  保存时校验，读取时再校验一次（白名单可能已经改小，暂存目录可能挪动）。
- **相对路径**（文件路径行的 `Folder`，下载、删除传入的 `path`，上传传入的 `subPath`）：
  拒绝绝对路径、盘符、`\\` 开头、`..` 段、`:`（防 NTFS 备用数据流）、控制字符；`\` 统一换成 `/`。
  上传的 `subPath` 例外：结构性的问题（绝对路径、盘符、`\\` 开头、`..` 段、控制字符）照样拒绝，
  其他非法字符（含 `:`）按文件名规则清洗成 `_`。
  拼接后再做一次「规范化 + 前缀判断」，确认仍在根路径（对 `Folder`）或这一行的文件夹（对 `path`、`subPath`）里，作为纵深防御。
- **文件名清洗**：`\ / : * ? " < > |` 和控制字符换成 `_`；开头的点换成 `_`；去掉末尾的点和空格；
  `CON`、`PRN`、`AUX`、`NUL`、`COM1`–`COM9`、`LPT1`–`LPT9` 前面加 `_`；清洗后为空则用 `file`。
  不含后缀的部分最多保留 60 个字符，保证整个文件名在 UTF-8 下不超过 255 字节（群晖等 NAS 的上限）。
- **后缀**（只在上传时）取清洗后文件名的扩展名，转小写，必须在这一行的 `AllowedExtensions` 里。
- **大小**（只在上传时）超过 `MaxSizeMb` 拒绝。分片上传在初始化时就按声明的大小先拦一次，合并后按实际大小再拦一次。
- **下载不看后缀**：只读的行里本来就有各种后缀的老文件。
  但相对路径里任何一段以 `.` 开头，都当作文件不存在：测试连接的探针文件、覆盖时的临时文件、系统隐藏文件都是这种。
  签名直链同样处理。上传的文件名和 `subPath` 经过清洗不会以点开头，所以业务文件不受影响。

### 4.2 三种命名规则

| 规则 | 相对路径 | 用在哪 |
|---|---|---|
| 年/月/原名_短ID | `{yyyy}/{MM}/{清洗后的原名}_{8 位随机十六进制}{后缀}` | 附件类。人能看懂、不会重名 |
| 业务指定路径 | `{subPath}/{清洗后的文件名}`，`subPath` 可空，每一段都按文件名规则清洗 | 打印模板、安装包这类路径本身有业务含义的 |
| 日期/GUID | `{yyyyMMdd}/{GUIDv7 的 N 格式}{后缀}` | 不在乎可读性、只求安全 |

年月和日期取**服务器本地时间**：文件夹是给人在资源管理器里翻的，按本地日期分才符合直觉。

写入都用 `FileMode.CreateNew`。年/月/原名_短ID 撞名时重新生成一次短 ID 再试。

业务指定路径撞名时按 `OnConflict` 处理：

- `Reject`：返回「文件已存在」。
- `Overwrite`：先写到同一文件夹里的临时文件 `.{文件名}.uploading-{随机}`，写完再替换目标：
  Windows 上用 `File.Replace`（目标正被读取时也能替换，替换失败先还原旧文件），其他平台用 rename（`File.Move(..., overwrite: true)`）。
  写到一半失败时，旧文件原样保留，临时文件删掉。不能先截断旧文件再写。

业务指定路径的 `subPath` 来自前端，能上传这一行的人就能覆盖这个文件夹里的任何同名文件。
所以覆盖类的行应当配上传角色；配置页在「同名覆盖 + 上传角色为空」时给出警告。

## 五、接口

上传和下载分成两个控制器、两个服务、两组路由。配置管理是另外两个控制器，文件路径一个、文件服务器一个。
四个控制器都标 `[Module("FilePath")]`，可经 `Api:DisabledModules` 一起关掉。

### 5.1 配置接口

`SysFilePathController`，路由前缀 `api/v1/sys/file-path`：
分页、详情、新增、编辑、删除、测试连接，
以及批量在线状态和环境信息（白名单根目录、当前平台能不能用账号连接，配置页拿来给提示和候选），这两个都是 GET。

`SysFileServerController`，路由前缀 `api/v1/sys/file-server`：
分页、详情、新增、编辑、删除、测试连接、批量在线状态，
以及下拉选项（GET，给文件路径的编辑弹窗选服务器用）。

- 全部 `[RolePermission]`，对应第七节的菜单按钮。
- 两边的新增、编辑、删除都加 `[RequireReauth]`：文件服务器存着账号密码，文件路径决定文件写到哪、谁能下载。
  测试连接不落库，不加。
- 测试连接测的是**弹窗里当前填的内容**，不要求先保存，免得为了测试先存一个可能写错的配置。
  接口接收表单内容，走和保存相同的校验（白名单、主机账号一致）。编辑已有的文件服务器时，密码留空表示用已保存的密码。
  - 文件服务器：连接（填了账号时）→ 根路径存在 → 可读（取到第一个条目就停，不列完整个目录）。
  - 文件路径：可写的行在文件夹里写入、读回、删除一个 `.smartadmin-probe-{GUID}` 文件，文件夹不存在时先创建；只读的行只检查文件夹存在。
  - 单次超时 5 秒（`WaitAsync`），超时报「超时」。
- 批量在线状态：并行对每行检查「根路径或文件夹是否存在」，单行超时 3 秒，不写文件、不落库。
  多副本部署时它反映的是处理这次请求的那个副本能不能访问。

### 5.2 上传接口 `FilePathUploadController`

路由前缀 `api/v1/sys/file-path/upload/{code}`：

| 方法 | 路由 | 说明 |
|---|---|---|
| POST | `upload/{code}` | 单文件上传，multipart：`file`，可选 `subPath` |
| POST | `upload/{code}/chunk/init` | 分片初始化：文件名、大小、可选 `subPath`、SHA-256。先做只读、后缀、大小、角色校验，通过才返回 `uploadId` |
| POST | `upload/{code}/chunk` | 上传一个分片：`uploadId`、`index`、分片内容 |
| POST | `upload/{code}/chunk/complete` | 合并、校验 SHA-256 和大小、按规则写入文件夹 |

返回 `{ path, name, size, viewUrl }`：`path` 是相对路径，`name` 是原始文件名，`viewUrl` 是签名直链。

- `viewUrl` 只在调用者也满足这一行的下载角色时返回，否则为 `null`。
  能上传不等于能下载；而且同名覆盖的行上，链接有效期内读到的可能已经是别人后来覆盖进去的内容。
- `uploadId` 由服务端随机生成，并绑定**当前用户 + 编码**。别人拿到这个 Id 也续传不了，同一个文件也不会因为哈希相同被不同用户共用一个分片会话。
- 分片先暂存在 `StagingPath/{uploadId}/`，合并后再写到文件夹，写完删掉暂存。
  断点续传只在同一次上传内有效：分片和合并遇到网络错误、超时、5xx、文件夹暂时不可访问时按 1、2、4 秒退避重试三次；
  合并报缺片时补传那一片再合并一次，只补一轮；任一片最终失败就取消其余在途的分片。关页面或重选文件要整个重传。
- 合并时文件夹不可访问或暂存读写失败，会话和已传分片保留，可以原样再合并一次；合并成功，或者认领合并之后核对没通过（哈希不符、规则已经不允许、业务路径撞名）才结束会话；缺片时会话保留，补传后再合并。
- 超过 `StagingTtlHours` 没有新分片的会话由后台清扫。
- 单文件上传的请求体沿用框架默认上限（Kestrel 约 28.6 MB，IIS 30 MB），不调大。
  前端组件对超过 20 MB 的文件自动走分片，所以 `MaxSizeMb` 配得再大也不受请求体上限影响。
- 多副本部署时，同一个上传的分片可能落到不同副本上，`StagingPath` 要放在共享卷上，或者负载均衡开会话保持。

### 5.3 下载接口 `FilePathDownloadController`

路由前缀 `api/v1/sys/file-path/download/{code}`：

| 方法 | 路由 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `download/{code}?path=&name=` | 登录 + 下载角色 | 一律附件下载（`Content-Disposition: attachment`），加 `nosniff`，支持 Range 断点续传 |
| GET | `download/{code}/view?path=&exp=&sig=&name=` | 匿名，验签名 | 签名直链。只有图片和 PDF 这几类安全类型内联显示，其余一律按附件下载 |

- `name` 可选，只决定下载时浏览器保存的文件名：清洗后，后缀强制换成磁盘文件的真实后缀，所以不进签名。
  不传时用磁盘上的文件名。业务想让用户下到原始文件名，就把上传返回的 `name` 也存进业务表，下载时带上。

签名直链：

- 签名是 `HMAC-SHA256(子密钥, "{code}\n{path}\n{exp}")`。子密钥从 JWT 签名密钥按新的用途标签 `smart:file-path-view` 派生，不和现有的 `smart:file-view` 共用。
- **必须带有效期**，不签发永久链接。默认 `LinkTtlMinutes`，签发时可以另传。
- 改编码、路径、有效期中的任何一个，签名都验不过。
- 由后端代码按需签发，比如业务列表接口给每行图片带一个 `viewUrl`、给不登录的客户端签发安装包的下载链接。
  业务表里存相对路径，不存链接。
- 内联类型白名单按后缀判断（`.png .jpg .jpeg .gif .webp .bmp .pdf`），不信上传时客户端报的 Content-Type，排除 `.svg` 和 HTML 类。
  这张表在新控制器里单独定义，不引用 `SysFileController` 的。

### 5.4 角色鉴权

上传、下载接口不挂菜单按钮，标 `[ActiveSession]`（登录即可进入），再按这一行配置的角色判断：

- 超管放行。
- 角色列表为空：所有登录用户都可以。
- 否则：当前用户**已启用**的角色和列表有交集才放行。
  `GetUserRoleIdsAsync` 不过滤停用的角色，这里要自己过滤。

这样业务用户不需要被授予系统模块的菜单。内核规定系统模块的菜单只能授给内置角色，
如果上传下载挂在系统菜单的按钮上，业务角色就拿不到权限。

文件服务器的账号属于后端，和登录用户无关：用户能不能上传、下载只看这里的角色判断。

已知限制：用户级单独授权（给某个用户额外允许或拒绝菜单）不影响这里的范围，这里只认角色。

### 5.5 错误码

在 44000–44999（文件上传）区间里划出 44100–44199 给文件路径，不复用 44001–44006。至少需要区分：

- 文件路径：编码不存在或已停用、编码已存在、只读、无上传权限、无下载权限、后缀不允许、超过大小上限、
  同名文件已存在、相对路径非法、文件不存在、文件夹不可访问、分片缺失、分片校验不一致。
- 文件服务器：不存在或已停用、名称已存在、根路径不在白名单内、没配白名单时根路径碰到程序目录或暂存目录、填了账号但根路径不是共享路径、
  同一主机账号不一致、仍被文件路径引用不能删除、数据保护密钥是临时密钥不能保存密码。

具体编号和 `msgKey` 由实施者分配。

「文件夹不可访问」带一个原因参数，前端据此显示可读的提示，完整的异常和系统错误码写日志。原因至少有：
拒绝访问、找不到网络路径、共享不存在、账号或密码错误、账号被锁定或停用、凭据冲突、超时。

## 六、后端组件

| 组件 | 职责 |
|---|---|
| `IFileServerService` | 文件服务器的增删改查、密码加密、主机账号一致性校验、测试连接、批量在线状态、下拉选项 |
| `IFileServerConnector` | 访问文件夹之前确保已连接。Windows 实现见 8.1；其他平台和没填账号的服务器什么都不做 |
| `IFilePathConfigService` | 文件路径的增删改查、缓存、测试连接、批量在线状态 |
| `IFilePathResolver` | 按编码取启用的行和它的文件服务器、调连接器、校验相对路径、拼出完整路径。上传和下载服务都用它 |
| `IFilePathUploadService` | 校验、命名、写入、分片会话；`DeleteAsync(code, path)` 也在这里 |
| `IFilePathDownloadService` | `OpenReadAsync(code, path)`、`GetFullPathAsync(code, path)`（给 BarTender 这类要完整路径的程序） |
| `IFilePathLinkSigner` | 签发和校验签名直链。接口放 Core，实现放 AspNetCore |
| `IFilePathAccessChecker` | 第 5.4 节的角色判断，只在 HTTP 接口上调用 |

- 后端代码直接调上传、下载服务时**不做角色判断**，由调用它的业务自己负责；只读、后缀、大小、路径校验照常生效。
- 全部 `TryAdd*` 注册；命名、清洗、路径解析、角色判断拆成 `protected virtual` 步骤，消费者可以子类化覆写单步。
  新的扩展点加进 `ReplaceabilityContract`。
- 上传、下载出错时，把 `IOException`、`UnauthorizedAccessException` 和连接器的失败转成「文件夹不可访问」并带原因，不让 500 冒出去。
- 不进 `/health/ready`：文件服务器暂时不可达不应该让整个应用被判为未就绪。
- 上传成功、两张表的增删改记操作日志。下载不记，和现有文件下载一致。
  密码字段名命中操作日志的敏感字段名单，入参里的密码自动打码。

## 八、文件服务器认证与部署

### 8.1 Windows：内核用账号连接

文件服务器填了账号时，连接器在第一次访问它之前调 `WNetAddConnection2W`（`mpr.dll`，P/Invoke，不引入依赖）：

- 资源类型 `RESOURCETYPE_DISK`，不分配盘符，远程名取根路径里的 `\\主机\共享` 部分，
  `dwFlags = 0`（不记进用户配置文件，不在下次登录时恢复）。
- 连接属于后端进程的登录会话。之后进程里访问这个共享的文件操作，都用这套凭据。
- 连接器按主机记着当前用的是哪套凭据（账号和密码的指纹，账号不区分大小写）。
  配置改了，包括别的副本改的（经缓存失效传过来），下次访问时先 `WNetCancelConnection2W` 断开本进程连着这台主机的所有共享，再用新凭据连。
  断开不强制：还有文件开着时断不开，就先继续用旧连接，下次访问再换。
  测试连接也走这套逻辑，测完不断开，下次正常访问时发现凭据和已保存的不一样，自然换回来。
- 同一台主机的连接操作串行，避免并发请求同时去连。
- 这个调用是阻塞的，主机不通时可能卡十几秒，放在线程池里跑并加超时。超时只让这次请求失败，后台那次调用自己结束。
- 按服务器熔断：网络类失败（找不到网络路径、超时）后 30 秒内，这台服务器的上传、下载、删除直接报「文件夹不可访问」，原因沿用上次的；
  30 秒后放一个真正访问文件服务器的请求去试探，连得上就恢复（这个请求本身因为文件不存在、撞名之类的原因失败也算连得上），网络类失败再挡 30 秒。测试连接和在线状态不受熔断拦截，网络类失败不打开熔断，连得上（含拒绝访问这类失败）就关闭熔断。
  每台服务器另有在途上限（默认 16，可在子类覆写），满了直接报「文件夹不可访问」，原因为「繁忙」。熔断状态按副本各自保存。
- 返回 1219（凭据冲突）时，先断开这台主机的所有共享再重连一次，常见于后端重启前用旧密码连过。
  还冲突就报「凭据冲突」：同一登录会话里有别的程序用另一套凭据连着同一台主机。
  所以部署时让后端用独立的运行身份，不和其他程序共用。
- **账号或密码错误时不自动重试**（1326 登录失败、86 密码错误、1909 账号锁定、1330 密码过期、1331 账号停用）。
  这套凭据记为失败，直到配置改了或有人点测试连接才再试。
  否则每个上传下载请求都去试一次错密码，几分钟就能把域账号锁住。
  网络类的失败（找不到网络路径等）过 30 秒再试。
- 没填账号的文件服务器不调这些函数，直接用后端的运行身份访问，见 8.3。

本地开发用 `dotnet run` 时，后端跑在开发者自己的登录会话里。
如果资源管理器正用开发者自己的账号打开着同一台 NAS，会报凭据冲突。这时开发环境的文件服务器账号留空，用开发者自己的身份访问。

### 8.2 Linux / Docker：宿主机挂载

内核不连接，由宿主机用 CIFS 挂载共享：

- 挂载参数写 `vers=3.1.1`（NAS 不支持时写 `vers=3.0`）、凭据文件（权限 600）、
  `uid`/`gid` 与容器里运行后端的用户一致，再把挂载点映射进容器。
- 文件服务器的根路径填容器里看到的挂载路径，白名单填挂载根目录，账号留空。
- 在 Linux 上，配置页把账号和密码输入框置灰，提示「由宿主机挂载时提供」。
  已经填了账号的行（比如从 Windows 环境迁过来的数据）在 Linux 上忽略账号，第一次用到时记一条警告日志。

### 8.3 运行身份与文件服务器侧

- 不在内核里保存账号也可以：Windows 后端以专用账号运行（IIS 应用程序池标识或 Windows 服务的登录身份），
  服务器和 NAS 在同一个域时用域账号，根路径写主机名而不是 IP，这样能走 Kerberos。文件服务器的账号留空即可。
- 文件服务器侧：访问账号不放进管理员组，只给需要的共享读写权限；SMB 最小协议设为 SMB2，关闭 SMB1。
- 密码存在库里，安全性取决于数据保护密钥。生产环境要配置持久的数据保护密钥（和 TOTP、第三方登录用的是同一套），否则不能保存密码。

## 十一、测试

后端（xUnit + WebApplicationFactory，用临时目录充当文件服务器根路径并放进白名单）：

- 路径校验：`..`、绝对路径、盘符、`\\` 开头、`a:b`、控制字符、`\` 与 `/` 混用，都被拒绝；合法路径拼接后落在文件夹内。
- 白名单：根路径不在白名单内被拒；`\\nas01\files2` 不被 `\\nas01\files` 误放行。
- 文件名清洗：非法字符、开头的点、保留设备名、末尾点和空格、超长名截断后不超过 255 字节。
- 三种命名规则的输出（注入固定的 `TimeProvider` 和随机源）；年/月/原名_短ID 撞名重试。
- 同名拒绝；同名覆盖成功替换；覆盖时写入中途失败，旧文件内容不变、没有残留临时文件。
- 只读的行拒绝上传，且不要求后缀和上限；可写的行缺后缀或上限保存被拒；后缀、大小上限（单文件和分片两条路都测）。
- 下载：任何一段以点开头的路径当作不存在（直接下载和签名直链都测）；`name` 的后缀被换成真实后缀。
- 角色：列表为空、命中、未命中、超管、角色停用后不算数；后端服务方法不做角色判断；没有下载角色时上传结果的 `viewUrl` 为空。
- 分片：初始化即拦截不合规文件；缺片；SHA-256 不一致；`uploadId` 换一个用户或换一个编码用不了；过期会话被清扫。
- 签名直链：改编码、路径、有效期任一项验签失败；过期失败；安全类型内联、其他类型按附件下载。
- 文件服务器：接口不返回密码；留空不改；清空账号连带清空密码；临时数据保护密钥时拒绝保存密码；
  填了账号但根路径不是共享路径被拒；同一主机不同账号被拒；被引用时不能删除；停用后其下文件路径拒绝上传下载。
- 测试连接：测未保存的表单内容，校验规则和保存一致。
- 连接器：用替身实现验证访问前先确保连接、凭据变了会重连、账号或密码错误后不再重试直到配置改变。
  真实的 `WNetAddConnection2W` 靠手工验证。
- 配置改动后缓存失效，下一次上传按新配置走。
- 回归：现有文件上传的测试一条不改、全部通过，证明旧功能没被碰到。
- `ReplaceabilityTests` 覆盖新服务的预注册优先。

SQLite 默认跑即可；新功能没有方言敏感的查询，不加进 SqlServer 分支的子集。

前端（vitest）：`FilePathUpload` 的分片阈值判断、成功事件的载荷；配置页的表单校验（可写的行后缀、上限必填，编码格式）。

手工验证（CI 里没有 SMB 环境）：

- Windows + 内核保存账号：后端以默认的应用程序池身份或服务身份运行，填账号后上传、下载、覆盖、测试连接都正常；
  改密码后不重启即生效；填错密码时测试连接报「账号或密码错误」，之后的上传下载不再拿错密码去试。
- Windows + 运行身份：账号留空，后端以有权限的专用账号运行，功能正常。
- Linux：CIFS 挂载后，从容器里上传、下载正常，生成的文件属主和挂载参数一致；配置页账号输入框置灰。
- 文件服务器断开：测试连接 5 秒内报超时，上传下载报「文件夹不可访问」，之后 30 秒内不再去连，登录和其他功能不受影响。
- 账号对某个共享没有权限：状态和测试连接显示「拒绝访问」。

## 十四、设计时定下的取舍

以下几点是设计时定下的，实施前可以再改：

- 签名直链取代「允许匿名下载」：链接必须带有效期，由后端按需签发。
- 上传和下载都按行配角色，上传也要配，防止有人覆盖安装包这类文件。
- 根目录白名单放在 appsettings，不放界面；它是可选的，不配时根路径直接在界面填，边界退到能改文件服务器的账号。
- 后缀和大小上限：可写的行必填、不继承「上传策略」，只读的行不填；下载不看后缀，点开头的文件不给下载。
- 文件服务器一个共享一行，同一主机只能用一个账号；Linux 上不用表里的账号。
- 账号或密码错误时不自动重试，防止把域账号锁住。
- 两张表的写操作都要求再认证（启用 TOTP 时生效）。
- 上传结果的 `viewUrl` 只给有下载权限的人；下载可传 `name` 指定保存的文件名。
- 测试连接测弹窗里当前填的内容。
- 菜单 Id 610–619，错误码 44100–44199，配置节 `SmartAdmin:FilePath`，分片的 `uploadId` 由服务端生成，日期取服务器本地时间。
