# 用户授权设计（角色授权 + 用户单独授权）

## 一、目标与边界

现在一个用户能用哪些菜单、能调哪些接口，只由他的角色决定（`sys_user_role` → `sys_role_menu`）。
本设计在角色授权之外，允许给单个用户**额外允许**或**拒绝**菜单节点，
授权可以带**有效期**，有效权限能**说清来源**，授权边界**按模块划分**。

做：

- 用户级「允许」与「拒绝」，拒绝优先。
- 授权有效期，到期自动失效。
- 模块新增「可转授」开关。超管能给用户授任何菜单；普通管理员只能授可转授模块里的菜单，模块内不再限制。
  系统模块固定不可转授，所以普通管理员授不了任何系统菜单。
- 「有效权限」视图：每个菜单为什么有效、来自哪里。
- 防止委派被滥用的三道约束：普通管理员不能对其他管理员做单独授权；普通管理员授出的「允许」必须限时（上限可配置）；
  「单独授权一览」让超管能复核全系统的例外。
  这三条针对「业务模块不管控」的固有风险：普通管理员新建一个账号给它授满业务菜单再自己登录，或两个管理员互相授权。
  限时让这类授权自动过期，一览让它能被发现，管理员互授则直接堵死。
- 系统模块的菜单只能授给内置角色（见 6.7）：超管在角色页给界面上新建的角色授权时，看不到「系统」模块，接口也拒绝；
  内核种子里的内置角色（固定 Id 1–999，如「系统管理员」）不受限。
  升级到本版本时，已经授给新建角色的系统模块菜单被物理删除。

普通管理员不是内置身份，他在系统模块里有什么由超管配的角色决定，本设计不为此加新机制。
内核已种好空授权的「系统管理员」角色（`DefaultRoleSeed`，`sys_admin`，备注「授权后分配给普通管理员」），推荐这样配：

| 页面 | 勾哪些 | 说明 |
|---|---|---|
| 用户管理 | 查询、新增、更新、删除、重置密码、启停、导入导出（按需），加「用户-授权菜单」 | 普通管理员的主要工作 |
| 角色管理 | 只勾「角色-查询」「角色-授权用户」 | 角色增删改、授权菜单、数据范围在服务层只允许超管（`EnsureSuperAdmin`），勾了也只会得到 41003 |
| 业务模块 | 他自己要用的菜单 | 按需 |

上面两页都在系统模块里，按 6.7 只能授给内置角色，所以普通管理员用的就是内置的「系统管理员」角色，不能另建一个。
再配一个数据范围角色（如「本机构及以下」）决定他能管哪些用户。
需要普通管理员能任命同级时，把「系统管理员」标为「可转授」，他就能把这个角色分给范围内的人；默认不标。

内核不强制「系统模块只能有这两页」，那是超管的配置选择。内核保证的是另一件事：
不管超管怎么配角色，普通管理员都不能经单独授权扩大任何人（含他新建的账号）在系统模块的权限，系统模块的权限只来自超管配的角色。

不做：

- 给角色授权菜单、配置角色数据范围、角色增删改，仍然只有超管能做。除 6.7 的「系统模块菜单只授内置角色」外，角色授权本期不动。
- 审批流与按需激活（eligible → activate）。
- 角色级拒绝。
- ABAC、关系型授权（Zanzibar 一类）。本内核的鉴权单位是路由码，行级由数据范围负责。
- 用户级数据范围。数据范围仍只来自角色。
- 对超管生效。超管照旧全量放行，不能给超管建用户授权。

## 二、参考的主流做法

| 系统 | 用户单独授权 | 合并方式 | 拒绝 | 防越权 / 封顶 | 时效 |
|---|---|---|---|---|---|
| Django | `user_permissions` | 与组权限叠加 | 无 | — | — |
| Laravel Spatie | 直授权限 | 与角色权限同样参与检查，文档建议优先给角色 | 无 | — | — |
| ABP | 用户级授权与角色级并列 | 任一来源禁止即禁止，否则任一来源允许即允许 | 有，一票否决 | 非管理员只能编辑自己已持有的权限 | — |
| AWS IAM | 用户、组、角色都可挂策略 | 并集 | 显式拒绝覆盖一切允许 | 权限边界与已授权限取交集 | — |
| Azure RBAC + PIM | 角色分配给用户 | 叠加 | 拒绝分配优先，但只有平台能建 | — | 起止时间、按需激活、审批、复核、审计 |

取用的结论：

1. 默认拒绝，允许取并集，用户授权与角色授权并列。
2. 例外收紧用显式拒绝，拒绝优先；拒绝只开在用户级，并且必须能在界面上解释清楚。
3. 委派授权要有边界。ABP 的边界是「只能授自己持有的」；本设计改用模块做边界：
   系统模块是管理面，只有超管能授；业务模块由普通管理员自主分配，不要求他自己持有。
   这与仓库已有的「角色可转授」（`SysRole.IsDelegatable`）是同一思路，只是粒度从角色换成模块。
4. 授权可以限时（PIM）。
5. 直授是例外，常规授权仍走角色，界面和文档都这样引导。

## 三、术语

| 术语 | 定义 |
|---|---|
| 角色授权 | `sys_role_menu` 一行：角色被授予一个菜单节点。 |
| 用户授权 | `sys_user_menu` 一行：对一个用户的一个菜单节点做「允许」或「拒绝」，可带到期时间。 |
| 生效中的用户授权 | 到期时间为空，或到期时间晚于当前时间的用户授权。 |
| 有效菜单 | 按第四节规则算出的、该用户最终可用的启用菜单节点集合。 |
| 有效权限码 | 有效菜单里各节点 `Permission` 拆开去重后的集合，`[RolePermission]` 用它比对。 |
| 授权来源 | 一个菜单为什么有效或无效：来自哪些角色、用户允许、用户拒绝、已过期。 |
| 授权人 / 目标用户 | 发起用户授权的当前用户 / 被授权的用户。 |
| 普通管理员 | 非超管、但有效权限码里含 `PUT:/api/v1/sys/user/menu`（能做单独授权）的用户。作为目标用户时也按这个判定。 |
| 委派授权 | 普通管理员（非超管）发起的用户授权。 |
| 可转授模块 | `SysModule.IsDelegatable == true` 的模块：普通管理员可以把其中的菜单授给或拒给用户。为空或为 false 都按不可转授处理。 |
| 菜单所属模块 | 沿 `ParentId` 上溯到根目录，取根目录的 `ModuleId`。不挂在任何模块下的菜单视为不可转授。 |

## 四、计算规则

对非超管用户：

- `R` = 该用户启用中的角色所授予的菜单 Id（现有口径，停用角色不贡献）。
- `A` = 该用户生效中的「允许」授权的菜单 Id。
- `D` = 该用户生效中的「拒绝」授权的菜单 Id。
- `D*` = `D` 加上 `D` 中每个节点在菜单树里的全部子孙。
- **有效菜单 `E` =（`R` ∪ `A`）−`D*`，再只保留启用的菜单。**

由此推出：

- 拒绝优先：同一节点既在 `R` 或 `A` 里又被拒绝，结果是无效。
- 拒绝一个目录或页面，它下面的页面和按钮一并无效，不会出现「页面没了、按钮接口还能调」。
- 拒绝作用在节点上，不作用在权限码上：被拒节点的某条权限码，如果还由另一个有效节点携带，这条码仍然有效。
  这样拒掉一颗按钮，不会连带拒掉别的页面共用的接口（例如 `GET:/api/v1/sys/menu/tree` 同时挂在好几颗按钮上）。
- 侧栏菜单树、门户模块列表照旧从有效菜单反推，祖先目录的脚手架逻辑不变。
  被拒目录的子孙都不在 `E` 里，所以被拒目录不会因为脚手架被加回来。
- 没有任何用户授权记录的用户，结果与现在完全一致。

超管：直接全量，用户授权记录不参与计算，也不允许为超管创建。

用户授权只授功能、不授数据。数据范围仍只来自角色；没有任何启用角色的用户，数据范围按现有口径是「仅本人」
（`DataScopeProvider.ComputeAsync`）。所以只靠用户授权、没有角色的用户能打开页面、能调接口，但只看得到自己创建的数据。
界面上给没有角色的用户授权时提示这一点。

## 五、数据模型

新增实体 `SysUserMenu`，表 `sys_user_menu`，继承 `BaseEntity`（自动带 `Id`、`CreateTime`、`CreateUserId`、`UpdateTime`、`UpdateUserId`、`IsDelete`）：

| 列 | 类型 | 说明 |
|---|---|---|
| `UserId` | long | 目标用户 |
| `MenuId` | long | 菜单节点 |
| `Effect` | int，枚举 `UserMenuEffect { Allow = 1, Deny = 2 }` | 允许 / 拒绝 |
| `ExpireTime` | DateTime?，可空 | 为空 = 长期；非空 = 到这个时刻失效 |
| `Remark` | string，最长 200，可空 | 授权理由 |

- 唯一索引 `(UserId, MenuId)`：一个用户对一个节点只有一条记录。
- 保存按**变更集**，不做整份替换：新增的插入，修改的更新，移除的物理删除（避免软删残行撞唯一索引），没动的行原样保留。
  这样每行的 `CreateUserId` / `CreateTime` 就是授权人与授权时间，`UpdateUserId` / `UpdateTime` 是最后修改人与时间。
  整份替换会把没动的行也删了重插，授权人信息被重置成本次保存的人；两个管理员同时编辑时，后保存的还会静默删掉对方刚加的记录。
  对授权数据，这两种丢失都不可接受。
- 保存时校验：菜单存在；同一次变更里同一菜单只出现一次；到期时间晚于当前时间；目标用户存在且未删除。
- 到期判断与审计字段使用同一个时钟口径（实施第一步核对 `CreateTime` 写入的是本地时间还是 UTC，`ExpireTime` 与比较都照它）。

`SysModule` 新增一列：

| 列 | 类型 | 说明 |
|---|---|---|
| `IsDelegatable` | bool?，可空 | 可转授。与 `SysRole.IsDelegatable` 同一写法：可空是因为 CodeFirst 不能给老表加不带默认值的非空列 |

- 只有 `true` 算可转授，`null` 和 `false` 都不可转授。老库升级后存量模块是 `null`，默认收紧。
- 内置「系统」模块（`BUILTIN_MODULE_ID`）在代码里固定不可转授：读取时一律按 false，保存时忽略传入值，界面上开关置灰。
- 新库的种子：「系统」为 false，「业务中心」为 true。超管在模块管理里新建模块时，表单默认打开。
- 这一列是超管的设置，不能随内核升级被种子覆盖。现状是 `DefaultModuleSeed` 开着 `SyncOnUpgrade`、没写 `SyncColumns`，
  升级时按排除法刷回除审计列与 `IsDelete` 以外的全部列（`DatabaseInitializer` 的种子同步逻辑），照这样每次升级都会把超管关掉的「业务中心」重新打开。
  所以模块种子改为列白名单，只同步内核拥有的结构列（`Code`、`ApiPrefix`、`DefaultRoute` 等，实施时逐列定），
  `IsDelegatable`、标题、排序、启用、备注留给用户，与菜单种子、配置种子的做法一致。
  附带的行为变化：超管改过的内置模块标题、排序、启用，升级后不再被刷回，写进 CHANGELOG。
- 老库升级时，白名单不含 `IsDelegatable`，「业务中心」保持 `null`，与其它存量模块一样按不可转授处理。

## 六、后端组件

### 6.1 计算规则的唯一实现

新增纯函数类 `UserMenuGrantRules`（`SmartAdmin.Services`，public static）：
输入 `R`、用户授权行、菜单的 `(Id, ParentId, Enabled)` 列表和当前时间，输出有效菜单 Id 集合，
以及「下一个到期时间」：该用户所有用户授权记录里，晚于当前时间的最早那个 `ExpireTime`，没有则为空。
不去判断那条记录到期会不会真的改变结果，一律按它封顶缓存，宁可多算一次。
第四节的所有规则只在这里实现一次，单元测试直接测它。

### 6.2 两处聚合点

- `RbacPermissionProvider.LoadFromDatabaseAsync`：在算出 `R` 之后调 `UserMenuGrantRules`，再取有效菜单的权限码。
  现在「没有角色就直接返回空」的短路要改：没有角色但有用户允许时也要继续算。
- `MenuService.ComputeMyModulesAsync` / `ComputeMyMenuTreeAsync`：同样用有效菜单代替 `R`。
- 两个类都**不加主构造器参数**（对继承它们的消费者是源码破坏性变更，由可替换性契约守住），
  读 `sys_user_menu` 走已有仓储的 `Db` 逃生舱口，查询用「预取 Id + Contains」，不用子查询，保证四种数据库可移植。
- 新增的一步拆成 `protected virtual` 方法，消费者可以单独覆写。

### 6.3 缓存

- 权限码缓存（`CacheKeys.UserPermissions`）与门户缓存（模块列表、菜单树）的过期时间，取「配置值」与「下一个到期时间」（见 6.1）中较小的一个。
  到期后下一次请求自然重算，不需要后台任务。配置值为 0（永不过期）时，有到期记录的用户照样按到期时间封顶。
- 保存用户授权后：失效该用户的权限码缓存，门户代际 +1。
- 菜单的修改与删除（含启停、移动父节点，都经更新；`MenuService` 在这两处调 `IRbacService.InvalidatePermissionsByMenuAsync`）：
  该方法的实现里，除了现有的「经角色授予该菜单的用户」，再失效**所有存在用户授权记录的用户**。
  拒绝会扩展到子孙，菜单移动会改变扩展结果，精确圈定代价高；用户授权本就是例外，这个集合小，过量失效无害。
  新建菜单不调这个方法，也不需要：新菜单还没有被任何角色或用户授予，不会出现在任何人的有效菜单里。
- 模块「可转授」开关的变化不影响任何缓存：它只在保存用户授权时参与校验，不参与有效菜单的计算。

### 6.4 授权服务与越权守卫

新增接口，`TryAddScoped` 注册，默认实现类 public、方法 virtual，并登记进可替换性契约：

- `IUserMenuGrantService`
  - `GetGrantsAsync(userId)`：目标用户的用户授权记录，每条带授权人、授权时间、最后修改人、到期时间、备注。菜单已不存在的记录不返回。
  - `ApplyChangesAsync(userId, upserts, removes)`：按变更集保存（见第五节），事务内执行，提交后失效缓存并发布事件。
  - `GetGrantPageAsync(query)`：单独授权一览，分页。筛选：用户（账号 / 姓名）、菜单、效果、状态（生效中 / 7 天内到期 / 已过期）、授权人。
    非超管只看得到自己数据范围内用户的记录（`IDataScopeGuard.ResolveScopedUserIdsAsync`）。
    查询沿用仓库「预取 Id + Contains」的写法，不用跨表子查询。
  - `GetEffectiveAsync(userId)`：授权弹窗需要的全部数据，一次取齐：
    - 每个菜单的有效与否、授权来源（角色名列表、允许、拒绝、到期时间、是否已过期）；
    - 当前授权人对该节点是否可授（`grantable`：超管恒为 true；普通管理员看菜单所属模块是否可转授）；
    - 被拒节点里**仍然有效的权限码**，以及携带它们的其它有效节点（节点级拒绝的「漏网接口」，界面据此提示）；
    - 当前授权人能否编辑这个目标用户（`targetEditable`）及不能的原因码（自己、超管、范围外、对方是管理员），界面据此整体只读并说明；
    - 委派授权最长天数（超管为空），界面据此限制到期时间的可选范围；
    - 模块清单（Id、标题、是否可转授），供弹窗按模块分组。
      授权弹窗因此不依赖 `GET /api/v1/sys/module/list`：那个端点要「模块-查询」权限，只管用户和角色的普通管理员没有，调了会 403。
      这也符合权限设计指南第三节「跨页面的数据源不靠顺手勾别页的查询权限」。
- 读接口（`GetGrantsAsync`、`GetEffectiveAsync`）同样做数据范围校验：非超管只能读自己数据范围内用户的授权，否则 `UserOutOfDataScope`。
  一个人的权限构成本身是敏感信息，不能靠猜 Id 读到范围外用户的。
- 保存成功后经 `IEventBus` 发布 `UserMenuGrantsChanged`（目标用户、操作人、新增 / 修改 / 移除明细）。
  内核自己不订阅；消费者可以接通知、外部审计或告警，不用改内核。
- 模块关闭「可转授」后，其中已有的用户授权照旧生效，只是普通管理员不能再改；撤销要超管动手。关闭开关不是撤销。
- `IUserMenuGrantPolicy`：`EnsureGrantableAsync(targetUserId, 变更集)`，规则依次为：
  1. 目标用户是自己：拒绝，`CannotOperateSelf`（42029）。对所有授权人生效，超管也不例外。
  2. 目标用户是超管：拒绝，`SuperAdminProtected`（42007）。对所有授权人生效。
  3. 授权人是超管：放行，不再做下面几条。
  4. 目标用户不在授权人的数据范围内（`IDataScopeGuard.IsUserInScopeAsync`）：拒绝，`UserOutOfDataScope`（41005）。该码现有文案只说「授予角色」，改成泛指「授权」。
  5. 目标用户也是普通管理员（其有效权限码含 `PUT:/api/v1/sys/user/menu`）：拒绝，新增码 `TargetIsDelegatedAdmin`（41007，文案：对方是管理员，只有超管能为其单独授权）。
     管理员之间的权限只由超管调整，堵住两个管理员互相授权或互相拒绝。
     判定看目标用户当前的有效权限码，所以某人被分进管理员角色之后，原先给他做授权的普通管理员就不能再改他的记录。
  6. 变更集里每一条效果为「允许」的新增或修改，到期时间必须非空，且不晚于「当前时间 + 委派授权最长天数」。
     违反时拒绝，新增码 `DelegatedGrantExpiryInvalid`（41008，文案带上最长天数）。
     「拒绝」不要求限时：它只会收紧权限。
     最长天数是配置项 `SmartAdmin:Security:DelegatedGrantMaxDays`（`AdminSecurityOptions` 新增属性，默认 90，0 表示不限）。
     长期权限应当走角色，单独授权本来就是临时例外，这与 PIM 的限时分配同一思路。
  7. 变更集里的**每一条**（新增、修改含只改备注、移除，「允许」与「拒绝」都算），菜单都必须属于可转授模块，
     否则拒绝，新增码 `MenuNotGrantable`（41006，文案：该菜单所属模块不允许转授）。
     不要求授权人自己持有这些菜单。
     移除也要校验，是因为删掉超管加的一条系统模块「拒绝」等于放大权限，删掉一条系统模块「允许」也是在改超管的决定。
     变更集之外的记录不校验，也不会被碰到：用户名下有超管在系统模块授过的记录时，普通管理员照样能保存自己在业务模块的改动。
- 菜单所属模块的计算（沿 `ParentId` 上溯到根目录取 `ModuleId`）目前是 `MenuService` 的私有方法 `RootModuleId`，
  抽成公共静态方法，`MenuService` 与守卫共用，避免两份上溯逻辑。

### 6.5 端点与菜单种子

挂在 `UserController`，都标 `[RolePermission]`，写端点加 `[RequireReauth]`：

| 端点 | 用途 |
|---|---|
| `GET /api/v1/sys/user/{id}/menus` | 取用户授权记录 |
| `GET /api/v1/sys/user/{id}/menus/effective` | 取有效权限与来源（含 `grantable`） |
| `PUT /api/v1/sys/user/menu` | 按变更集保存，请求体 `{ userId, upserts: [{ menuId, effect, expireTime?, remark? }], removes: [menuId] }` |
| `GET /api/v1/sys/user/menu-grants/page` | 单独授权一览（分页 + 筛选） |

- 变更集重复提交结果相同（幂等），所以仍用 `PUT`；仓库里没有用过 `PATCH`，不为此引入。
- 操作日志记录的请求体（脱敏后、按 `ParamMaxChars` 截断）正好就是这次的增改删明细，不会因为整份集合过长被截掉关键内容。

- 菜单种子新增按钮 `Id = 239`，`ParentId = 230`，标题「用户-授权菜单」，排序 9，
  挂 `GET:/api/v1/sys/menu/tree` 和上面四条码（回显、提交、一览拆开授没有意义，照「角色-授权菜单」的归法）。
- `PUT:/api/v1/sys/user/menu` 加入高敏权限清单（`HighSensitivityPermissions`）。
- 错误码新增 `MenuNotGrantable = 41006`、`TargetIsDelegatedAdmin = 41007`、`DelegatedGrantExpiryInvalid = 41008`，中英文文案同步。
- 模块的新增、更新端点与 DTO 带上 `IsDelegatable`（沿用模块管理现有的权限码，不加新按钮）。模块列表返回它，供前端显示开关。

### 6.6 关联清理

- 用户软删：用户授权记录保留，恢复后照旧生效（与角色关联的处理一致）。
- 用户彻底删除（回收站清除）：在 `UserRecycleBinType.BeforePurgeAsync` 里一并物理删除其用户授权记录。
- 菜单彻底删除：菜单的回收站类型现在没有清除钩子（`ServicesSetup` 里 `AddRecycleBinType<SysMenu>` 未覆写 `BeforePurgeAsync`），
  `sys_role_menu` 的关联行也不清，留下无害的孤儿行。本期给菜单加清除钩子，一并物理删除指向它的用户授权记录；
  读取用户授权时也过滤掉菜单已不存在的行，双保险。角色关联的孤儿行是既有问题，不在本期范围，另行记录。

### 6.7 系统模块菜单只授内置角色

系统模块（`BUILTIN_MODULE_ID`）是管理面：除了超管自己，只有内核种子里的内置角色能持有其中的菜单。

- 内置角色：`SysRole.IsBuiltin`，即 `Id` 落在内核种子区间 1–999（`SmartSeedIds.KernelMax`）。
  它是只读的计算属性（不建列），出参里带着，前端据此决定授权弹窗显示什么。
  消费者自己种子里的角色（Id ≥ 1000）和界面上新建的角色（雪花 Id）一样，都不是内置角色。
- 「系统菜单」指内核自带的系统菜单：沿 `ParentId` 上溯到根目录，根目录的 `ModuleId` 是系统模块，且根目录 `Id` 在内核种子区间（≤ `SmartSeedIds.KernelMax`），整棵子树都算。
  消费者自建的目录（`Id` ≥ 1000）即使挂在系统应用下也不是系统菜单：升级不清理、授权不拦、角色页照常显示；
  但它们仍属于系统应用，随模块不可转授，要委派须改挂到自己的应用。
- 角色授权弹窗：给非内置角色授权时，系统菜单的顶级节点不出现，系统应用下已没有别的节点时「系统」也从应用下拉里去掉；内置角色照旧显示全部。
- 接口：`RbacService.SetRoleMenusAsync` 在非内置角色的菜单集合里发现系统模块菜单时，拒绝，新增码 `SystemMenuNotAssignable`（41009）。
  拆成 `protected virtual` 步骤，走已有仓储的 `Db` 逃生舱口读菜单，不改主构造器。
  系统 / 未认证上下文（种子、启动任务、消费者无登录上下文的代码）不受限，与 `EnsureSuperAdmin` 同一约定。
- 升级清理：从种子版本低于 7 的库升级上来的那一次启动，库就绪后物理删除「非内置角色 × 系统模块菜单」的 `sys_role_menu` 行，
  每一行写一条 Warning 日志（角色名、编码、菜单标题、菜单 Id），失效受影响用户的权限码缓存与门户代际。
  空库、平时重启、关了种子（不走版本闸门）都不执行。删除不可恢复，CHANGELOG 按破坏性变更写明并提示升级前备份 `sys_role_menu`。
- 已知限制：之后有人把一个顶级目录挪进系统模块，已授给新建角色的该目录菜单不会被自动收回。
  超管打开该角色的授权弹窗保存一次即可收回（弹窗不显示这些节点，打开时已把它们从已授集合里去掉，保存是整份替换）。
- 用户单独授权不受这条影响：超管仍能把系统模块菜单单独授给某个用户，普通管理员按 6.4 碰不到系统模块。

## 七、前端

- 用户页行「更多」新增「授权菜单」：需要 `PUT:/api/v1/sys/user/menu`；超管那一行和自己那一行不显示。
  叫「授权菜单」而不叫「用户授权」，与角色页同名同义，也避免和角色页的「授权用户」（把用户分进角色）混淆。
- 弹窗复用 `GrantMenuSheet` 的壳（定高、底栏常驻），列表用新组件 `UserGrantMenuTable`，
  复用 `grantMenuGroups.ts` 的分组、搜索、模块切换，**角色页的 `GrantMenuTable` 不改**，避免回归。
- 每个节点一行：
  - 左侧：来自哪些角色（只读标签）、当前是否有效。
  - 右侧：三态「跟随角色 / 允许 / 拒绝」，选了允许或拒绝后可填到期时间和备注。
  - 授权人不可授的节点（`grantable = false`，即普通管理员看到的不可转授模块，系统模块整块都是）三态置灰，悬浮说明「该模块只允许超管授权」。
- 模块管理页的表单与列表加「可转授」开关；内置「系统」模块的开关置灰并说明原因。
- 角色页「授权菜单」：非内置角色不显示「系统」模块（见 6.7），弹窗里一行提示「系统自带的菜单只能授给内置角色」；内置角色不变。
- 选「拒绝」时，如果这个节点有权限码仍由别的有效节点携带，就地提示「以下接口仍可调用，来自 ×× 」，避免管理员以为拒掉了接口其实没有。
- 弹窗内第二个页签「有效权限」：只读列出有效菜单与来源，每条单独授权显示授权人、授权时间、到期时间、备注。
- 模块分组用 `GET .../menus/effective` 带回的模块清单，不调模块列表接口。
- 目标用户没有任何角色时，弹窗顶部提示「该用户没有角色，数据范围为仅本人」。
- 文案提示「常规授权请走角色，这里只放例外」。
- 保存只提交变更集：前端对比打开时的状态，算出新增、修改、移除。
- 普通管理员操作时，选「允许」必须填到期时间，日期选择器的上限是「今天 + 最长天数」，默认就取这个上限；超管可留空。
- `targetEditable = false`（例如对方是管理员）时，弹窗整体只读，顶部说明原因，只能看不能改。
- 单独授权一览：放进用户页工具栏的「更多 ▾」（低频动作，按表格标准不占业务按钮位），需要 `GET:/api/v1/sys/user/menu-grants/page`。
  打开抽屉，SmartTable 列出：用户、菜单（带所属模块）、效果、到期时间与状态、授权人、授权时间、备注；
  按状态、效果、授权人筛选；行操作「去调整」直接打开该用户的授权菜单弹窗。
- `npm run gen:api` 生成新端点类型；中英文 i18n；种子菜单标题的翻译键。

## 八、兼容性与升级

- 不改 `IRbacService`、`IPermissionProvider`、`IMenuService` 的成员，不改 `RbacPermissionProvider`、`MenuService`、`RbacService` 的主构造器。
- 新表由 CodeFirst 自动创建；存量用户没有用户授权记录，行为不变。
- `sys_module.IsDelegatable` 由 CodeFirst 加为可空列。老库升级后所有存量模块都是 `null`，按不可转授处理：
  普通管理员在超管打开某个模块的开关之前，授不了任何菜单。CHANGELOG 的升级说明写明这一步。
- 新按钮 239 随种子进老库（实施时核对种子升级对「新增行」的处理与 `SysSchemaVersion` 是否需要 bump）。
- 消费者如果整体替换了 `IPermissionProvider` 或 `IMenuService`，他们的实现不认新表，用户授权不会生效；文档写明。
- 模块种子改为列白名单（见第五节），内置模块的标题、排序、启用不再随升级刷回，CHANGELOG 写明。
- 已知限制：授权改动在接口层立即生效（权限码不在 JWT 里，每次请求按缓存取），
  但目标用户已经打开的页面不会实时刷新侧栏与按钮，要刷新页面或重新登录。角色变更现在也是这样（`RbacService` 没有推送），保持一致，不在本期加推送。
- **破坏性**：升级时删除非内置角色上的系统模块菜单授权（6.7）。依赖新建角色访问系统模块页面的项目，升级后这些用户会失去入口，
  要改用内置「系统管理员」角色。
- 版本：次版本号（新增功能），升级说明顶部加粗提示这条破坏性变更，写进 CHANGELOG。

## 九、测试

先锁现状，再加新行为：

1. 回归：核对现有测试对「角色授权 → 权限码 / 菜单树 / 模块」的覆盖（停用角色、停用菜单、祖先脚手架），缺的先补并跑绿。
2. 纯函数单测（`UserMenuGrantRules`）：并集、拒绝优先、拒绝扩展到子孙、过期忽略、节点级拒绝与共享权限码、最近到期时间。
3. 集成测试（WebApplicationFactory，`UserMenuGrantTests`）：
   - 允许后权限码、菜单树、模块都出现；拒绝后都消失；删除记录后恢复。
   - 没有角色、只有用户允许的用户也能用。
   - 已过期记录不生效；缓存过期时间被最近到期时间封顶。
   - 越权：对自己、对超管、范围外用户、不可转授模块的菜单（新增、修改、删除三种动作各一条），各自返回对应错误码；超管不受限。
   - 可转授模块里，普通管理员能授自己并不持有的菜单。
   - 模块开关：内置系统模块传 true 也保存不进去；`null` 按不可转授处理；新库种子里业务中心为 true。
   - 用户名下有超管授的系统模块记录时，普通管理员只提交业务模块的变更集，保存成功，系统模块记录原样不动。
   - 菜单移动父节点后，拒绝的扩展结果随之变化（缓存被失效）。
   - 用户彻底删除、菜单彻底删除后，对应记录被清掉。
   - 变更集：没动的记录 `CreateUserId` / `CreateTime` 不变；两个管理员先后提交各自的变更，互不覆盖。
   - 读接口：普通管理员读范围外用户的授权与有效权限，返回 `UserOutOfDataScope`。
   - 校验：到期时间早于当前时间、同一菜单重复、菜单不存在，各自被拒。
   - 模块关闭「可转授」后，已有授权照旧生效，普通管理员改它被拒。
   - 有效权限接口：被拒节点的「仍然有效的权限码」与来源节点正确；返回模块清单，普通管理员不需要模块查询权限也能取到。
   - 保存成功后发布 `UserMenuGrantsChanged`，明细与变更集一致。
   - 管理员互授：普通管理员对另一个普通管理员保存，返回 `TargetIsDelegatedAdmin`；超管可以；目标被分进管理员角色后，原授权人再改被拒。
   - 委派限时：普通管理员授「允许」不带到期时间、或超过最长天数，返回 `DelegatedGrantExpiryInvalid`；「拒绝」不受限；超管不受限；配置为 0 时不限。
   - 单独授权一览：普通管理员只看到范围内用户的记录；状态筛选（生效中 / 7 天内到期 / 已过期）结果正确；超管看全部。
   - 种子升级：模拟升级后「业务中心」的 `IsDelegatable` 保持超管设的值（`SeedUpgradeTests` 的路数）。
   - `sys_module` 新增可空列在四种数据库上的建表与升级（`CodeFirstNullableUpgradeTests` 的路数，该类已在 SqlServer 子集里）。
   - 系统模块菜单只授内置角色：超管给新建角色授系统菜单返回 `SystemMenuNotAssignable`，授业务菜单成功，给内置角色授系统菜单成功；
     角色出参带 `isBuiltin`；从版本 6 升级时非内置角色的系统菜单被删、内置角色的保留，版本不变的重启不删。
4. 现有守卫自动覆盖：`PermissionCodeConsistencyTests`（端点与种子双向一致）、`HighSensitivityConsistencyTests`、`ErrorCodeLocaleConsistencyTests`、`ReplaceabilityTests`。
5. 前端：分组与三态状态的纯函数 vitest；e2e 一条主流程（给无角色用户允许一个页面 → 该用户登录能看到 → 改成拒绝后看不到）。
