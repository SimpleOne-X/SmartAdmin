# ADR 0010 — 多租户(共享库模式):反转"不做多租户"非目标

- 状态:**已采纳**(2026-09-15)
- 取代:`rebuild-design.md` 中「多租户:不做(不是推迟,是整体不做);实体不带租户维度,保持模型简单」及非目标清单中的「不做多租户」条目;`rebuild-design.md` §4.2 扩展点表「`IDataScopeProvider` | 机构树数据范围 | 自定义数据隔离维度(如租户)」的表述**仍然有效**——本 ADR 是该扩展点提示的正式落地,但实现方式是新增独立的 `ITenantScoped` 硬隔离维度,而不是复用/替换 `IDataScopeProvider`(理由见「决策 2」)。
- 相关:`docs/superpowers/specs/2026-09-15-multi-tenancy-shared-database-design.md`(完整设计,含数据模型、隔离边界、认证链路、消费方影响);`docs/plans/kernel-consistency-and-modernization.md` 第 2 节(前置评估草稿)。

## 背景

`rebuild-design.md` 在原始设计中把多租户列为明确非目标,理由是"保持模型简单"。评估阶段(2026-09-15)核实现状:内核已有的 `IOrgScoped`/`DataEntity` 机构数据权限范式成熟,但**零个内置实体实际使用它**——全部 `Sys*` 表走 `BaseEntity`,机构数据权限对系统表是靠 `IDataScopeGuard` 手工在个别 Service 里叠加查询条件实现的;`IRepository<>` 恒打主库;既有的 multi ConfigId(`AdditionalDatabases`)机制是启动时静态挂载,官方文档明确"不会按租户自动切库";四个实体基类没有任何 `TenantId` 预留。也就是说当前架构**谈不上"开箱即用支持多租户"**。

维护者确认有明确的多租户消费方需求,决定投入实现,范围限定为"共享库模式"(一期),"独立库/混合模式"(二期)只做数据模型层面的最小预留,不实现动态路由。

## 决策

### 1. 反转非目标,范围限定为一期共享库

废止 `rebuild-design.md` 中"不做多租户"的表述。新的产品立场:多租户是内核的正式能力,一期以**共享库 + 字段过滤**方式实现,二期(未来,不含在本次工作量内)在此基础上让消费方业务表可选路由到独立连接串。

### 2. 隔离模型:新增独立维度,不复用机构数据范围

`TenantId` 与 `OrgId` 正交,是两个不同语义的维度:机构数据范围(`IOrgScoped`/`DataScopeType`)回答"同一租户内,这个角色能看多少机构的数据";租户隔离(新增 `ITenantScoped`)回答"这一行数据根本不属于当前租户,不该被看见"。后者是硬安全边界,过滤器**不设**类似 `DataScopeType.All` 的"全部可见"逃逸条件——一个角色被误配成"数据范围=全部"时,机构数据权限的意图是"看到本租户全部机构",而不应该意外看穿其他租户。这是为什么不直接把 `IOrgScoped` 改造成租户维度、而是新增一个并列接口。

### 3. 租户识别:账号固定归属一个租户

登录只需账号密码,后端按账号反查所属租户,`Account` 保持全平台唯一。放弃"账号可跨租户、登录后选择/切换"和"按子域名/租户代码识别"两个备选方案——前者需要处理跨租户切换后的 token 重签发与权限刷新,改动量明显更大;后者是典型对外 SaaS 做法,需要网关/域名层配合,超出内核纯软件改动范围。已知代价:两个不同租户不能各自注册同名账号,详见设计文档 §9。

### 4. 平台级数据保持共享,不按租户隔离

字典(`SysDict`)、系统参数配置(`SysConfig`)、AI 服务商/模型配置继续全平台共享——这条延续了 AI 模块既有的"厂商配置是系统级"原则(`docs/plans/ai-management.md`),不因多租户改造而改变。菜单结构(`SysMenu`)本身也保持全平台统一,按租户区分的是角色对菜单的授权集合,不是菜单树本身。

### 5. 二期"混合模式",不是"整租户搬家"

参照 SqlSugar 官方文档(donet5.com"仓储+多租户"/"SAAS 分库")的"基础信息库 + 业务库"划分:二期即便某租户选择"独立库"隔离模式,内核自身的机构/用户/角色/菜单授权数据也**继续留在共享主库**,只有消费方自己的业务表可以路由到该租户的独立连接串。这大幅缩小了二期的实际范围——不需要重做内核数据层,只需要让 `IRepository<>` 对消费方业务实体这一类支持按 `SysTenant.ConnectionConfigId` 动态解析连接。本 ADR 只确认这个方向和 `SysTenant` 上预留的 `IsolationMode`/`ConnectionConfigId` 两个字段,不批准二期的具体实现——二期需要独立评估、独立设计文档。

### 6. 平台管理员与租户内超管分层

现有超管(`sadm` claim)语义收窄为"租户内超管",仍属于某个具体租户。新增"平台管理员"(`TenantId` 为 null,不属于任何租户),唯一能管理 `SysTenant` 本身;大概率由内核种子里的初始超管账号(`Id=1`)天然充当,不新增独立账号体系。平台管理员默认**看不到**任何租户域数据(过滤器对 `TenantId=null` 的上下文恒不匹配),"跨租户排障视角"明确不在本次范围。

## 后果

- **正面**:内核获得真正意义上的多租户能力,机构数据权限范式的成熟经验(全局过滤器 + AOP 自动填充锚点)被复用到新维度上,改动集中、边界清晰;二期范围因"基础信息库/业务库"划分而显著收窄,风险可控。
- **负面/成本**:这是一次跨全部四层包(Core/SqlSugar/Services/AspNetCore)+ 前端一个新页面的改造,涉及全部内置 RBAC 实体迁移基类、登录链路改动、四个数据库方言的升级迁移测试,工作量明显大于"共享库"字面听起来的规模,需要按独立大版本规划,可能需要标记为 breaking change。
- **已知权衡**:账号全平台唯一(见决策 3),牺牲了"每个租户账号命名空间独立"的灵活性,换来登录页/前端零改动。
- **对已发布版本的影响**:`SmartAdmin` 已在 nuget.org / npm 发布多个版本,存在真实的升级用户,"当前无外部真实部署"这一前提不成立。此前落地的菜单 Id 整体重排(为 2xx 预留"租户管理"目录)按"全新设计"处理、未设计升级迁移脚本——种子按主键 Id 判存、只插缺失行,直接挪号会让老库在升级后同时留有新旧两套内置目录/页面/按钮。**本条 ADR 落地(或再合回 `main`)之前,必须为这次重排及后续所有结构性调整(`TenantId` 回填等)一并设计一次性升级迁移脚本,不能再直接改种子数据了事。**

## 不在本 ADR 范围

- 二期独立库/混合模式的具体路由实现、事务处理、跨库查询——留待二期单独立项设计。
- 具体需要迁移到租户维度的内置实体清单与字段细节——见配套设计文档,随实施计划阶段核实源码后收敛。
- 是否需要"平台管理员代入租户排障"这类跨租户运维视角——明确排除在外,不是遗漏。
- 前端"所属租户"只读徽章是否要做——产品细节,留给实施前最终确认,不影响本 ADR 的架构结论。
